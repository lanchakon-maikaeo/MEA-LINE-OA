# กติกาข้อมูลห้ามหาย

เจ้าของสั่งวันที่ 1 พ.ย. 2569 ว่า**ข้อมูลห้ามหายเด็ดขาด รวมถึงตอนย้าย** ทุกแผนย่อยต้องทำตามหน้านี้ ถ้าขั้นไหนพิสูจน์ไม่ได้ว่าข้อมูลครบ ห้ามทำขั้นถัดไป

## ข้อมูลที่ต้องพาไปครบ

| ข้อมูล | อยู่ที่ไหนบน E5 | พิสูจน์อย่างไร |
|---|---|---|
| ฐานข้อมูล `faoj` | Postgres | `move_manifest --deep`: จำนวนแถวและ digest ของเนื้อหาทุกตาราง, ค่า sequence ทุกตัว, เลข W/R/P, ลำดับ audit |
| ไฟล์แนบและไฟล์ roster ที่ seal ไว้ | `/srv/faoj/data/media` | sha256 ของ**ทุกไฟล์**ในโฟลเดอร์ (ไม่ใช่เฉพาะไฟล์ที่ DB อ้างถึง) ต้องตรงกันทั้งสองฝั่ง |
| ข้อความ LINE ที่เข้ามาตอนปิดระบบ | ยังอยู่ที่ LINE | เปิด Webhook redelivery ไว้ และ inbox กันซ้ำด้วย `webhookEventId` (`webhook_inbox_event_key`) |
| key ที่ใช้ถอดรหัสข้อมูล | `app.secret.env` และ `backup.secret.env` | `decrypt-check` บน GCP: ถอดรหัส API key ที่เก็บใน DB และอีเมลใน roster ได้จริง |
| backup เก่า | OCI Object Storage stanza `production` | เก็บไว้อย่างน้อย 30 วันหลังย้าย พร้อม cipher pass ในตัวจัดการรหัสผ่าน |
| n8n | DB `n8n` | ไม่ย้าย เพราะ workflow มากับ release แต่เก็บ dump ไว้เป็นหลักฐาน |

## ทางที่ข้อมูลอาจหาย และสิ่งที่กันไว้

| # | ความเสี่ยง | สิ่งที่กันไว้ | ตรวจว่า |
|---|---|---|---|
| 1 | ระบบเปล่าบน GCP รับข้อมูลจริงก่อนย้าย แล้วข้อมูลนั้นถูกล้างตอน restore | ไม่มี ngrok, ไม่มี LINE token, เปิด `maintenance on` หลัง smoke และยังไม่แจ้ง URL ให้ใคร | `docker ps` ไม่มี ngrok และ `faoj maintenance status` เป็น on |
| 2 | ยังมีคนเขียนลง E5 หลัง dump (การ UPDATE ไม่ทำให้จำนวนแถวเปลี่ยน manifest เดิมจึงจับไม่ได้) | หยุด web, worker, n8n และ ngrok → ตั้ง DB ของ E5 เป็น read-only → ตรวจ `pg_stat_activity` ว่าไม่มี client อื่น | `--deep` ก่อนและหลัง dump ต้องตรงกัน |
| 3 | dump หรือ restore ไม่ครบ หรือเนื้อหาเพี้ยน | `pg_restore --exit-on-error` และ sha256 ของไฟล์ dump ต้องตรงกันทั้งต้นทางและปลายทาง | `move_manifest --deep --compare` |
| 4 | ไฟล์แนบหายหรือเสียระหว่างคัดลอก | `tar` เก็บ owner และ mode | รายการ sha256 ของทั้งโฟลเดอร์ตรงกัน และ attachment ของ `verify_restore` ไม่มี missing หรือ mismatched |
| 5 | key ผิด ข้อมูลที่เข้ารหัสอยู่จะเปิดไม่ได้ ซึ่งเท่ากับข้อมูลหาย | merge key ตามตารางในแผน 5 และเจ้าของมีสำเนาในตัวจัดการรหัสผ่าน | `decrypt-check` ผ่าน และ `escrow-check` hash ตรงกัน |
| 6 | ข้อความ LINE ที่เข้ามาช่วงปิดระบบหาย | redelivery ต้องเปิด (ไม่เปิดห้ามย้าย), ปิดระบบให้สั้นที่สุด และ inbox กันซ้ำ | ให้บัญชีทดสอบส่งข้อความระหว่างปิด แล้วข้อความต้องเข้ามาหลังเปิด |
| 7 | สั่งลบผิดเครื่อง เช่น `DROP SCHEMA` ไปโดน E5 | คำสั่งที่ลบได้ต้องเช็ก `FAOJ_HOST=faoj-prod-gcp` ก่อน ไม่ตรงให้ปฏิเสธ ฝั่ง E5 ไม่มีคำสั่งลบเลย | อ่านโค้ดใน PR |
| 8 | backup บน GCP ไม่ทำงานหลังย้าย โดยไม่มีใครรู้ | `pgbackrest check`, full backup, restic snapshot และ restore drill **ในวันเดียวกัน** | drill ผ่าน `--deep --compare` |
| 9 | ถอยกลับ E5 หลังเปิด GCP แล้ว ข้อมูลที่เขียนบน GCP หาย | หลังเปิดแล้ว `back-to-e5` ต้องเป็นการ**ย้ายกลับ**ด้วยขั้นตอนและการตรวจชุดเดียวกัน ห้ามแค่สลับ ngrok | สคริปต์ปฏิเสธการสลับเฉย ๆ เมื่อ GCP เคยเปิดรับงานแล้ว |
| 10 | ลบ E5 หรือ backup เก่าเร็วเกินไป | E5 แช่ไว้แบบ read-only จนถึง 10 พ.ย. ส่วน stanza `production` และ dump ของรอบย้ายเก็บไว้ 30 วัน | – |
| 11 | Object Storage เต็ม ทำให้ backup ล้มเงียบ ๆ | เช็กพื้นที่ก่อนย้าย และให้ Mac healthcheck แจ้งเมื่อ backup ล่าสุดเกิน 2 ชม. | แจ้งเตือนทำงาน |
| 12 | Free Trial หมด เครื่องหยุด แล้วดิสก์ถูกลบใน 30 วัน | ตั้ง budget alert ที่ 50% และ 80%, ย้ายออกก่อนกลาง ม.ค. 2570 และ backup อยู่ที่ OCI ไม่ขึ้นกับ GCP | – |

## สำเนาข้อมูล ณ จุดที่หยุดเขียน (freeze)

1. E5 ทั้งเครื่อง: read-only เก็บไว้ถึง 10 พ.ย.
2. dump บน E5: `/srv/faoj/restore/move-<ts>/` (root 700)
3. dump บน GCP: path เดียวกัน
4. OCI Object Storage: pgBackRest `incr` และ restic snapshot ที่ทำหลัง freeze
5. Mac: `make backup-pull` รันหลังย้าย
6. GCP ที่เปิดใช้งานแล้ว

dump ทุกชุดมีข้อมูลส่วนบุคคล จึงเก็บเฉพาะในโฟลเดอร์ของ root แล้วลบทิ้งเมื่อครบ 30 วัน

## สิ่งที่การันตีได้และไม่ได้

- **การย้ายตามแผนการันตีว่าข้อมูลไม่หาย (RPO 0):** ต้องตรวจครบทุกข้อข้างบนก่อนเปิดรับงาน ถ้าข้อใดไม่ผ่าน E5 จะกลับมาให้บริการ โดยข้อมูลบน E5 ไม่ถูกแตะ
- **หลังย้ายแล้ว ถ้าเครื่องพังกะทันหัน ยังเสียข้อมูลได้ไม่เกิน 5 นาที** (`archive_timeout=300`) เท่ากับบน E5 ตอนนี้
  - Hyperdisk เก็บสำเนาไว้หลายชุดใน zone อยู่แล้ว VM พังเฉย ๆ จึงไม่ทำให้ดิสก์หาย
  - ลด timeout ลงไม่ได้ เพราะโควตา Object Storage ฟรีมี 50,000 request ต่อเดือน
  - ถ้าต้องการ RPO 0 แม้ตอนเครื่องพัง ต้องมี standby แบบ synchronous บนเครื่องที่สอง ซึ่งเกินงบ trial
