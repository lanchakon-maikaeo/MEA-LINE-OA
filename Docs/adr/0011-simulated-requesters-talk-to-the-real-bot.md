# ผู้แจ้งจำลองคุยกับบอทจริง ข้อความจากแม่แบบหรือโมเดลที่ผ่านการตรวจ และทุกอย่างย้อนกลับ

ผู้ใช้ให้นำ flow จากงานวิจัยการสร้างบทสนทนาจำลอง (ASCRIBE/S-ICOPD, GraphTOD) มาใช้ (10 ต.ค. 2569) งานวิจัยใช้กราฟเจตนา สุ่มเส้นทาง แล้วให้โมเดลภาษาสองตัวเล่นเป็นสองฝั่ง ตรวจผลด้วยกฎ และให้สร้างใหม่พร้อมคำแนะนำเมื่อไม่ผ่าน

**ที่เลือก:**
- จำลองเฉพาะฝั่งผู้แจ้ง อีกฝั่งคือบอทจริง โดย event ผ่านทางเก็บของ webhook (`line.store_events`) และตัวจัดการตา (`conversation.handle_inbox`) เดียวกับ LINE จริง บทสนทนาที่ผ่านจึงเป็นบทที่บอทจริงทำได้
- ข้อความของผู้แจ้งสร้างจากแม่แบบด้วยกฎเป็นค่าเริ่มต้น (ให้โมเดลเขียนใหม่ได้ ดูด้านล่าง) การลองใหม่แบบงานวิจัยมีสองชั้น:
  - ก่อนส่ง: ข้อความต้องตรงกับป้ายของบทสนทนาตามกติกาที่ใช้งาน ไม่ตรงก็สุ่มใหม่
  - หลังส่ง: ถ้าบอทไม่ไปต่อ ผู้แจ้งจำลองซ่อมแบบคน และนับเป็นจุดติดขัด
- ความผิดของบอทเป็นข้อค้นพบ ไม่ลองซ้ำจนผ่าน
- ขั้นของบทสนทนาอ่านจากข้อมูลของบอท (ขั้นของร่างเรื่อง, prompt) ส่วนการกระทำของผู้แจ้งจำลองใช้ได้เฉพาะปุ่มและข้อความที่บอทตอบจริง เปลี่ยนถ้อยคำบอทแล้วตัวจำลองไม่พัง แต่ถ้าปุ่มหายจะจับได้
- กองเจ้าภาพที่คาดหวังอ่านจากตารางความรับผิดชอบในเอกสารกติกาโดยตรง ไม่ผ่านโค้ดจัดเส้นทางที่กำลังตรวจ
- ทั้งรอบอยู่ในธุรกรรมที่ย้อนกลับ แต่ละบทใน savepoint ของตัวเอง ปิด AI และการส่งออก ใช้ได้เฉพาะ local, ci, staging
- หลังยื่นเรื่อง บางสถานการณ์ให้เจ้าหน้าที่ของกองเจ้าภาพขอข้อมูลเพิ่มผ่าน `services` เหมือนหน้าเว็บ (เพิ่ม 11 ต.ค. 2569) แล้วผู้แจ้งจำลองทักทาย ถามคำถาม กด "ไม่ใช่ข้อมูลเพิ่ม" หรือตอบข้อมูล ตัวตรวจ `info` ดูว่าข้อความถึงเรื่องเฉพาะเมื่อเป็นข้อมูล และบอทไม่บอกเรื่องที่เจ้าหน้าที่รอซ้ำ

**ให้โมเดลเขียนข้อความของผู้แจ้ง (ผู้ใช้อนุมัติ 10 ต.ค. 2569 "ทำต่อ"):**
- เลือกได้ตอนรัน (`--writer model --profile N`) ค่าเริ่มต้นยังเป็นแม่แบบ ใช้โปรไฟล์ AI ที่ผู้ดูแลตั้งไว้แล้ว ไม่เปิดเวอร์ชัน AI ของบอท และ AI ของบอทยังปิดระหว่างรัน
- โมเดลได้รับเฉพาะข้อความแม่แบบที่เป็นข้อมูลจำลองและผ่านการตรวจป้ายแล้ว ไม่ได้รับชื่อ รหัส หรือปุ่ม และมีเพดานจำนวนครั้งต่อรอบ
- ข้อความที่โมเดลเขียนต้องผ่านกฎเดียวกับแม่แบบ และต้องไม่มีสิ่งเหล่านี้:
  - คำสั่งเรื่องวิธีพิมพ์ปนมา
  - อักษรภาษาอื่น
  - การเขียนในบทเจ้าหน้าที่
  - เนื้อความเหลือจากข้อความเดิมไม่ถึงครึ่ง (เทียบคู่ตัวอักษร)
  - ความยาวเกินสองเท่าของข้อความเดิม
  - ความต้องการหรือความไม่แน่ใจของผู้แจ้งหายไป
  - ตัวเลข ชื่ออุปกรณ์ คำอันตราย หรือคำของเรื่องการใช้ไฟฟ้าหายหรือเพิ่ม
- ไม่ผ่านก็ส่งเหตุผลกลับให้โมเดลเขียนใหม่ในบทสนทนาเดิม ครบจำนวนครั้งแล้วใช้แม่แบบ โมเดลที่อ่อนจึงลดความหลากหลายได้ แต่ทำให้ผลตรวจบอทผิดไม่ได้
- รายการคำและเกณฑ์เหล่านี้อยู่ในกราฟ (`not_requester`, `keep_meaning`, `rewrite_overlap`, `rewrite_length`)

## Considered Options

- **ให้โมเดลภาษาเล่นทั้งสองฝั่งแบบงานวิจัย:** ไม่เลือก ฝั่งบอทที่โมเดลเล่นไม่ใช่บอทของเรา ผลที่ได้จึงทดสอบบอทจริงไม่ได้
- **ให้โมเดลเขียนข้อความผู้แจ้งโดยไม่มีแม่แบบ:** ไม่เลือก ป้ายของบทสนทนา (หมวด อันตราย การใช้ไฟฟ้า) จะไม่มีที่มาที่ตรวจได้ การให้โมเดลเขียนใหม่จากแม่แบบที่ผ่านการตรวจแล้วทำให้รู้ป้ายแน่นอน
- **ให้โมเดลอีกตัวตัดสินว่าข้อความที่เขียนใหม่ตรงความหมายไหม:** ยังไม่ทำ กฎตรวจได้แน่นอนและตรวจย้อนได้ ข้อความที่ผ่านกฎแต่เปลี่ยนความหมายเล็กน้อยยังมีได้ จึงให้ชุดประเมิน AI ที่ส่งออกเป็นชุดร่างให้คนตรวจ
- **รู้ขั้นจากถ้อยคำในคำตอบของบอท:** ไม่เลือก เปราะเมื่อปรับถ้อยคำตามแนว humanizer
- **เก็บบทสนทนาจำลองไว้ในฐานข้อมูลเพื่อสาธิต:** ไม่เลือก เรื่องด่วนจำลองจะเด้งถึง LINE ของเจ้าหน้าที่ที่เชื่อมไว้และกินโควตา ผลเก็บเป็นไฟล์ JSON lines แทน

## Consequences

- ด้วยแม่แบบ ความหลากหลายของภาษาต่ำกว่าคนจริง ด้วยโมเดลหลากหลายขึ้น แต่เล่นซ้ำได้ไม่ตรงคำเดิม (ไฟล์ JSON lines เก็บข้อความที่ใช้ไว้) ชุดประเมิน AI ที่ส่งออกเป็นชุดร่างให้เจ้าหน้าที่ตรวจ ไม่ใช่ชุดที่ล็อก
- การรันด้วยโมเดลส่งข้อความจำลองไปยังผู้ให้บริการ AI ที่อยู่ใน `AI_ALLOWED_HOSTS` และมีค่าใช้จ่ายตามจำนวนครั้ง
- บอทเพิ่มขั้นหรือช่องใหม่ ต้องเพิ่มในกราฟ (ช่องที่ไม่รู้จักและต้องตอบ ตัวจำลองตอบข้อความทั่วไปและบันทึกไว้ในหมายเหตุ)
- ระหว่างหนึ่งบท แถวที่ถูกล็อก เช่น ตัวนับเลขเรื่อง จะรอจนบทนั้นย้อนกลับ ควรรันบน staging เมื่อไม่มีผู้ใช้กำลังส่งเรื่อง
