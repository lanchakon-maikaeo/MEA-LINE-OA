# ผลประเมิน AI ที่เซ็นบนเครื่องที่ประเมินแล้วนำเข้า production

ต่อจาก [ADR 0001](0001-ai-draft-authority-and-evaluation.md) ผู้ใช้เลือก "ทาง ก" และตอบ Q1–Q7 วันที่ 24 ตุลาคม 2569

การเปลี่ยนไปใช้รุ่น AI ต้องมีผลประเมินที่ผูกกับโค้ดที่รันอยู่ (`source_digest`) และการตั้งค่าของรุ่น (`config_digest`) แต่การประเมินต้องเล่นร่างซ้ำในฐานข้อมูลเดโม production จึงประเมินเองไม่ได้ ผลคือหลัง deploy ทุกครั้ง production เปลี่ยนรุ่นหรือย้อนรุ่น AI ไม่ได้เลย ตรวจวันที่ 24 ต.ค. ยังพบว่า image ไม่มี `uv.lock` ทำให้ `source_digest()` บน production ล้มด้วย `FileNotFoundError` และหน้าแอดมิน AI ขึ้น 500 ถ้ามีรุ่นที่ประเมินผ่านแล้วแต่ยังไม่ได้ใช้

- **ที่ประเมิน (Q1):** Mac บนฐานข้อมูลเดโม ด้วยโค้ด commit เดียวกับ release ที่ production รันอยู่ ไม่มีไฟล์ค้าง
- **ลายเซ็น (Q2):** Ed25519 กุญแจลับอยู่บน Mac เท่านั้น (`manage.py make_ai_evidence_key`) production เก็บแค่กุญแจสาธารณะใน `AI_EVIDENCE_PUBLIC_KEYS` (`django.env` ไม่ใช่ค่าลับ) เอากุญแจออกจากรายการเมื่อไร ผลประเมินที่เซ็นด้วยกุญแจนั้นก็ใช้เปิดรุ่นไม่ได้ทันที
- **สิ่งที่ต้องตรง (Q3):**
  - **โค้ด:** `source_digest` ต้องเท่ากับของโค้ดที่ production รันอยู่ image ใส่ `uv.lock` แล้ว ไฟล์ที่ขาดให้ค่าที่ไม่มีการประเมินไหนตรง จึงไม่ผ่านโดยไม่ล้มหน้าเว็บ
  - **การตั้งค่า:** เทียบด้วยเนื้อหา (`portable_digest`) คือ model, timeout, max_tokens, temperature, JSON schema, base_url ของทุกโมเดลในลำดับและโมเดลคัดกรอง, pipeline, few_shot, typed_fields และเวลารวมของระบบ ไม่นับเลขรุ่น pk และเวลาเปลี่ยน key เพราะต่างกันทุกฐานข้อมูล `config_digest` เดิมยังใช้กับผลประเมินที่ทำบนเครื่องเดียวกัน
  - **การทดสอบ:** production ยังต้องทดสอบการเชื่อมต่อด้วย key ของตัวเองก่อนเปลี่ยนไปใช้
- **รุ่นบน production (Q4):** ถ้ามีรุ่นที่ตั้งค่าตรงกันและไม่ได้ถูกทำเครื่องหมายไม่ใช้ ผลประเมินจะไปติดที่รุ่นนั้น ถ้าไม่มี ระบบสร้างรุ่นใหม่ตามเลขของ production และหมายเหตุว่านำเข้าจาก vN ของเครื่องที่ประเมิน
- **ตัวอย่าง few-shot ไม่ตรง (Q5 ข):** นำเข้าได้แต่เตือนในหน้าแอดมิน AI และบันทึก `examples_match` ใน audit ผู้ใช้เลือกแบบนี้เพราะตัวอย่างจากข้อมูลจริงจะเกิดได้ก็ต่อเมื่อผู้ใช้บน production เริ่มถามแล้ว
- **ช่องทาง (Q6):** `manage.py import_ai_evidence --file … --username … --reason …` (รับ `-` จาก stdin ได้) และปุ่มอัปโหลดในหน้าแอดมิน AI ทั้งสองทางต้องเป็นผู้แก้ AI ต้องใส่เหตุผล และบันทึก SHA-256 ของไฟล์ commit และ key id ใน audit `ai.evidence_imported`
- **ขอบเขต (Q7):** เฉพาะงานอ่านข้อความ (extract) โมดูล `ai_evidence` เปิด `TASKS` ไว้ให้เพิ่มงานอื่นทีหลัง

ตอนเปิดใช้ ระบบตรวจลายเซ็นซ้ำจากรายงานที่เก็บไว้ จะแก้รายงานในฐานข้อมูลก็ไม่ผ่าน และจะผ่านต่อเมื่อโค้ดกับการตั้งค่ายังตรงอยู่เท่านั้น

## ขั้นตอนต่อ release

1. deploy release R ตามขั้นตอนของ main
2. บน Mac: checkout commit ของ R (ไม่มีไฟล์ค้างใน `operations`, `config`, `uv.lock`) แล้วประเมินรุ่นบนฐานข้อมูลเดโม
3. `manage.py export_ai_evidence --number N --key <กุญแจลับ> --out ai-evidence-vN.json`
4. นำเข้าบน production (คำสั่งหรือหน้าแอดมิน AI) → ทดสอบการเชื่อมต่อ → ผู้ใช้เปลี่ยนไปใช้เอง

## Considered Options

- **รัน image ของ release บน Mac:** ไม่เลือก commit เดียวกันให้ไฟล์ที่ hash ตรงกันอยู่แล้ว และง่ายกว่า
- **ให้ CI ประเมิน:** ไม่เลือก ต้องเอา API key ของผู้ให้บริการไปไว้ใน GitHub และเสียค่าเรียกทุก release
- **ไม่เซ็น เชื่อผู้แก้ AI ที่นำเข้า:** ไม่เลือก บัญชีเว็บที่รั่วจะปลอมผลประเมินได้
- **HMAC ด้วยกุญแจร่วม:** ไม่เลือก production จะถือกุญแจที่ใช้ปลอมได้ด้วย
- **ปฏิเสธเมื่อตัวอย่างไม่ตรง:** ผู้ช่วยแนะนำ แต่ผู้ใช้เลือกเตือนแทน (Q5)

## Consequences

- deploy ทุกครั้งทำให้ผลประเมินที่นำเข้าไว้หมดอายุเหมือนเดิม รุ่นที่ใช้อยู่ทำงานต่อได้ แต่จะเปลี่ยนรุ่นต้องประเมินที่ commit ใหม่และนำเข้าใหม่ (ราว 190 ครั้งต่อรุ่นสำหรับรุ่นที่อ่านช่องที่พิมพ์)
- กุญแจลับบน Mac ต้องสำรองไว้ในที่ปลอดภัยของเจ้าของ ถ้าหายให้สร้างใหม่แล้วเปลี่ยน `AI_EVIDENCE_PUBLIC_KEYS`
- งาน answer, triage, routing และ keywords ยังเปลี่ยนรุ่นบน production หลัง deploy ไม่ได้ จนกว่าจะเพิ่มใน `TASKS`
